## Дальше

### T7. Навык `/denodo:execute`

**Статус:** дальше
**Веха:** A

`SKILL.md` плюс `references/errors.md`. Справочник ошибок теперь про два класса: коды
Denodo и HTTP-статусы маркетплейса. Тексты ошибок VDP для первого класса уже собраны —
раздел 5 [отчёта T2](superpowers/specs/2026-09-08-spike-t2-ddl-over-9996.md): кодов у
них нет, только текст, справочник строится по подстрокам. Второй класс собран в разделе 7
[отчёта T11](superpowers/specs/2026-09-08-spike-t11-marketplace-api.md): статус HTTP плюс `code`, когда он есть; повторное удаление у тегов — `500`,
у категорий — `200`, у типов и серверов — `404`.

Вводные из T5 (раздел 7.3 спеки — набор команд и поведение): навык описывает агенту
`vql run FILE | -e`, `vql desc`, `api METHOD PATH`, `env check`; поле `error.kind`
(`usage`, `config`, `connection`, `refused`, `environment`) и коды выхода `0/1/2/3`;
у `vql run` ошибка сервера лежит в `statements[failed_at].error.message` — это и есть
подстрока для справочника; у `api` — `status` отдельно от `body`, тело бывает `null`.
Отдельный сценарий навыка — **нет профиля**: `error.kind = "config"` с текстом про
`env init`; агент просит человека выполнить `! ${CLAUDE_PLUGIN_ROOT}/scripts/denodo env init`
сам (команда интерактивна, пароль скрыт), а не собирает хост/логин/пароль в чате.
На production-профиле разрушительные операции отклоняются с `refused` — навык объясняет,
что `--allow-destructive` ставится только после подтверждения человека (6.3).
`allowed-tools: Bash(${CLAUDE_PLUGIN_ROOT}/scripts/denodo *)` — из раздела 5 спеки.

### T6. Ядро `/denodo:vql`

**Статус:** дальше
**Веха:** A
**Блокирует:** T8a, T8b, T8c, T8d

Рабочий цикл, конвенции с переопределением проектом, правила безопасности,
идемпотентность, карта навыков. Раздел 6 спеки.

Правило безопасности из 6.3 обязано накрывать и HTTP: удаление тега или категории в
маркетплейсе разрушительно ровно так же, как `DROP`, но слова `DROP` в запросе нет —
правило, сформулированное через ключевые слова VQL, такой вызов пропустит.

Из спайка T11 (раздел 6 [отчёта T11](superpowers/specs/2026-09-08-spike-t11-marketplace-api.md)): список разрушительных HTTP-вызовов
подтверждён на стенде, и среди них есть `POST` — `tags/vdp/synchronize` с неполным
списком стирает остальные импортированные теги, `element-management/all/synchronize`
с `proceedWithConflicts:"SERVER"` затирает локальные правки. Правило строится по методу
и пути, а не по глаголу. Идемпотентность 6.4 для HTTP — пара «найти по имени → `POST`
или `PUT`», потому что все операции идут по числовым `id`, которых в шаблоне быть не
может.

## Ждёт

### T8a. Навык `catalog`

**Статус:** ждёт (T6)
**Веха:** A

Три объекта: виртуальная база, папка, тег VDP. Формат — раздел 8 спеки.

Из спайка T2: у тега `ADD_TO` и `REMOVE_FROM` обязательны парой, представления только с
именем базы; `DROP FOLDER IF EXISTS` не удаляет папку с содержимым. Разделы 4.1 и 4.3
[отчёта](superpowers/specs/2026-09-08-spike-t2-ddl-over-9996.md).

### T8b. Навык `datasources`

**Статус:** ждёт (T6)
**Веха:** A

Семь объектов: JDBC, DF и JSON — источник и wrapper для каждого, плюс базовое
представление. Три набора шаблонов, самая тяжёлая из четырёх задач.

Из спайка T2: wrapper DF обязан перечислять все колонки файла — с частью колонок он
создаётся без ошибки, а базовое представление молча отдаёт ноль строк; у `CREATE TABLE`
после `CACHE OFF` нужен `TIMETOLIVEINCACHE DEFAULT`. Рабочие шаблоны DF-источника,
wrapper'а и базового представления — в `spikes/t2_ddl_over_9996.py`. Разделы 4.2 и 4.3
[отчёта](superpowers/specs/2026-09-08-spike-t2-ddl-over-9996.md).

### T8c. Навык `views`

**Статус:** ждёт (T6)
**Веха:** A

Три объекта: производное представление, интерфейсное представление, ассоциация.

Из спайка T2: в `CREATE INTERFACE VIEW` `SET IMPLEMENTATION` идёт до `FOLDER`, типы —
VQL-овские (`long`, не `bigint`); `ALTER INTERFACE VIEW ... SET IMPLEMENTATION`
работает. Рабочие шаблоны всех трёх — в `spikes/t2_ddl_over_9996.py`. Из спайка T11:
`one` — зарезервированное слово, `SELECT 1 AS one` не проходит парсер; `NULL` в
типизированной колонке — `CAST('text', NULL)`, массив в проекции собирается только
`NEST(...)` с `GROUP BY`.

### T8d. Навык `marketplace`

**Статус:** ждёт (T6)
**Веха:** B

Три объекта: тег маркетплейса, категория, external element. Единственный навык, где
шаблон — HTTP-вызов, а не VQL; он же проверяет на прочность правку раздела 8.

Из спайка T11 (разделы 3–6 [отчёта T11](superpowers/specs/2026-09-08-spike-t11-marketplace-api.md)): вызовы и тела для тега и категории
сняты со стенда; external element не создаётся одним вызовом — это цепочка «тип
элемента → тип провайдера (multipart) → custom external tool server → VQL контракта из
`vql-metadata` → реализация interface view → `synchronize`», то есть шаблон из пяти
HTTP-вызовов и VQL-фрагмента. Успех назначения — пустой список в ответе, а не `200`.
Удаление родительской категории каскадно удаляет потомков, удаление сервера — все его
элементы. Рабочая цепочка целиком — в `spikes/t11_marketplace_api.py`.

### T12. Верификация шаблонов на стенде

**Статус:** ждёт (T8a, T8b, T8c, T8d)
**Веха:** A для VQL-шаблонов, B для marketplace

`scripts/denodo verify` в тестовой базе `denodo_skills_test`, прогон, простановка пометок
`verified:`. Раздел 11.1 спеки.

Вынесена отдельной задачей, потому что это единственная работа, которой физически нужен
стенд, а для marketplace-части — ещё и поднятый маркетплейс.

Подкоманда `scripts/denodo verify` в T5 намеренно не сделана: ей нужен формат шаблонов
из T8a–T8d. Строится поверх `denodo_cli.commands.vql.run_statements` и
`commands.api.api_call`; интеграционные тесты `tests/integration/test_stand.py`
(включаются `DENODO_TEST_ENV=dev`) — образец уборки за собой.

### T13. Приёмка: сквозной сценарий

**Статус:** ждёт (T8a, T8b, T8c, T12)
**Веха:** A — закрывает её

Одной фразой на естественном языке довести до работающей витрины: база → папка →
файловый источник → wrapper → базовое представление → производное представление, с
проверкой `SELECT`.

Это критерий отбора из T1, повёрнутый в тест. Файловый источник взят намеренно: сценарий
замыкается на пустом стенде, без внешней СУБД.

### T9. Eval-сьют навыков

**Статус:** ждёт (T8a, T8b, T8c, T8d)
**Веха:** B

`evals/`: фраза → ожидаемый навык. Раздел 11.2 спеки.

## Открытые вопросы

- Судьба `docs/superpowers/specs/2026-09-04-denodo-skills-brainstorm-wip.md`: содержимое
  целиком перенесено в чистовую спеку, файл дублирует её и может разойтись. Удалить или
  оставить как историю обсуждения.
- `source: "./"` копирует в кэш плагина весь репозиторий — вместе с `docs/` (1149 строк
  спек) и `CLAUDE.md`. Проверено на локальной установке в T4. Работу навыков это не
  ломает, но пользователь тянет проектную документацию. Три выхода: оставить как есть,
  вынести плагин в подпапку (`source: "./plugins/denodo"`, расходится с разделом 5 спеки)
  или держать спеки в отдельной ветке. Решать до первой публикации.
- Язык публичных артефактов зафиксирован в T4 как английский: `description` в манифестах,
  а дальше `SKILL.md` и README. Проектная документация (`docs/`, `CLAUDE.md`) остаётся на
  русском. Не решено, нужны ли русские триггерные фразы в `description` навыков — вопрос
  всплывёт в T6 и станет предметом eval-сьюта T9.
- Объём `/denodo:query` в v1 остаётся минимальной дельтой (раздел 9 спеки). T1 его не
  менял: JSON-источник добавляет вложенные структуры, и это первый кандидат на
  расширение дельты — но только если T13 покажет, что без этого сценарий не замыкается.

## Сделано

- **T5. Слой исполнения `scripts/denodo`.** Launcher на stdlib (`DENODO_CLI_PYTHON` →
  `uv run --script` → venv в данных плагина → JSON с командой установки), пакет
  `scripts/denodo_cli` с профилями (`~/.denodo/profiles.toml`, формат зафиксирован в 7.4
  спеки), разбиением VQL на выражения, двумя транспортами (`vql_psycopg2`, `api_rest`),
  командами `vql run|desc`, `api`, `env list|check|init` и JSON-выводом с кодами выхода.
  141 юнит-тест без зависимостей, 8 интеграционных на стенде 9.5.1. Закрыт открытый вопрос
  T2 §3.5: при ошибке в середине строки с `;` сервер выполняет всё до неё и ничего после,
  без отката; клиент режет файл сам и сообщает индекс упавшего выражения. Разрушительные
  операции помечаются по правилу 6.3 (VQL — по ключевому слову, HTTP — по методу и пути)
  и на production-профиле требуют `--allow-destructive`. `verify` отложен до T12.
- **T11. Спайк: API Data Marketplace.** Риск №2 снят: пути и тела для тегов, категорий
  и external elements сняты с OpenAPI живого сервера и подтверждены на стенде;
  аутентификация — HTTP Basic учёткой VDP, `serverId` необязателен при одном сервере.
  Импортированные из VDP теги в маркетплейсе только на чтение — подтверждено (`403` на
  правку и назначение). External element в 9.5 не создаётся напрямую: он импортируется из
  interface view VDP через custom external tool server. Найдены разрушительные вызовы без
  `DROP`/`DELETE` в тексте (`tags/vdp/synchronize` с неполным списком стирает остальные
  импорты) и ловушка VQL (`one` — зарезервированное слово). Скрипт —
  `spikes/t11_marketplace_api.py` (121 шаг, 0 расхождений на 9.5.1), отчёт —
  [отчёта T11](superpowers/specs/2026-09-08-spike-t11-marketplace-api.md). Вводные разнесены по T5, T6, T7, T8c, T8d.
- **T2. Спайк: DDL через канал 9996.** Риск №1 снят: через `denodo+psycopg2` прошла
  вся VQL-цепочка v1 от базы до ассоциации, `CREATE OR REPLACE` и `DROP ... IF EXISTS`
  подтверждены для девяти типов, `api_rest` нужен только маркетплейсу. Скрипт —
  `spikes/t2_ddl_over_9996.py` (89 шагов, 0 расхождений на 9.5.1), отчёт —
  [спайк T2](superpowers/specs/2026-09-08-spike-t2-ddl-over-9996.md). Побочно
  найдены четыре ловушки клиента (автокоммит, `%`, `CONNECT DATABASE`, `text()`) и три
  ловушки VQL (парный `REMOVE_FROM` у тега, полный `OUTPUTSCHEMA` у wrapper DF,
  `TIMETOLIVEINCACHE` перед `ADD SEARCHMETHOD`) — разнесены по вводным T5, T7, T8a–T8c.
- **T4. Каркас плагина.** `.claude-plugin/plugin.json` (плагин `denodo`, версия 0.1.0) и
