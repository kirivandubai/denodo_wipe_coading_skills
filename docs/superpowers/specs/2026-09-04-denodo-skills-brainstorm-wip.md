# Denodo Skills для ИИ-агентов — брейншторминг (WIP)

**Статус:** в работе. Архитектурный путь брейншторминга. Подход к нарезке скиллов
выбран (вариант C, гибрид). Следующий шаг — презентация дизайна по секциям.
Дизайн-документ ещё не написан, план реализации не создан, код не пишется.

**Дата фиксации:** 2026-09-04 (обновлено в той же сессии)

---

## Исходная задача

Создать набор навыков (skills) для ИИ-агентов, которые создают объекты в платформе
Denodo. Цель — чтобы агент писал корректный VQL, не тратя токены на чтение
онлайн-документации и поиск примеров.

---

## Главный вывод: skills, а не MCP-сервер

Skills и MCP решают разные задачи и не являются альтернативами:

| | Skills | MCP-сервер |
|---|---|---|
| Что даёт | **знание** — как правильно написать VQL для объекта X | **руки** — выполнить, посмотреть каталог, проверить |
| Живёт | в файлах репозитория | в процессе с креденшелами к VDP |
| Стоимость в контексте | ~30 токенов на скилл (только `description`), тело читается по требованию | схемы всех тулов, постоянно |
| Решает исходную задачу | да | нет |

Три аргумента за skills-first:

1. **Progressive disclosure — ровно тот механизм, который нужен.** Фронтматтер
   скилла висит в контексте постоянно и стоит копейки; тело `SKILL.md` читается
   только при релевантности, а `references/*.md` — только когда нужен конкретный
   раздел.
2. **У Denodo уже есть официальный MCP-сервер, и он про другое.** Denodo MCP Server
   и Denodo AI SDK с MCP-режимом сфокусированы на Query RAG: natural language →
   `SELECT` по существующим витринам (потребление данных). Это не разработка
   объектов. Свой MCP ради DDL дублировал бы транспорт, который у Denodo и так есть
   (JDBC, Management API), и всё равно не дал бы знания VQL.
3. **Исполнение дешевле получить без MCP.** У агента уже есть Bash: JDBC через CLI,
   `curl` к Management API. Скилл описывает это в десятках строк, без отдельного
   процесса, конфига и постоянного налога на контекст.

Свой MCP-сервер имеет смысл рассматривать позже и только под задачу, которую скилл
плюс bash закрыть не могут — например, семантический поиск по каталогу из тысяч вьюх.

**Источники:**
- [Denodo MCP Server — User Manual](https://community.denodo.com/docs/html/document/denodoconnects/9.2-beta/Denodo%20MCP%20Server%20-%20User%20Manual)
- [Denodo AI SDK — User Manual](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20AI%20SDK%20-%20User%20Manual)
- [Virtual DataPort VQL Guide (latest / 9.5)](https://community.denodo.com/docs/html/browse/latest/en/vdp/vql/index)

## Решение по архитектуре: вариант C (гибрид)

**Выбран вариант C.** Ниже — все три рассмотренных подхода и обоснование выбора.

### A. Один зонтичный скилл + библиотека references

```
skills/denodo-vql/
  SKILL.md              ← роутер: "нужен JDBC-источник → references/datasources/jdbc.md"
  references/
    datasources/*.md
    views/*.md
    catalog/*.md
```

Постоянная стоимость — один `description`. Минус: агент всегда делает два чтения,
`SKILL.md` разрастается в оглавление, триггер один на всё — срабатывает либо слишком
часто, либо слишком редко.

### B. Много мелких скиллов, по одному на класс объектов

`denodo-datasources`, `denodo-base-views`, `denodo-derived-views`,
`denodo-catalog-structure`, …

Триггеры точные, одно чтение вместо двух, постоянная стоимость всё ещё копеечная
(10 скиллов ≈ 400 токенов фронтматтера). Минус: общее — подключение, исполнение,
конвенции именования, идемпотентность, разбор ошибок — либо дублируется в каждом
скилле, либо расползается.

### C. Гибрид: ядро + доменные скиллы ← ВЫБРАНО

```
skills/
  denodo-vql/           ← ядро: конвенции, идемпотентность, карта остальных скиллов
  denodo-execute/       ← как применить VQL: JDBC CLI и curl к Management API, разбор ошибок
  denodo-catalog/       ← databases, folders, tags, описания  (база v1)
  denodo-datasources/   ← + references/ по подтипам: jdbc, json, xml, df, excel, odata, s3
  denodo-views/         ← base views, wrappers, derived views
scripts/
  vql                   ← готовая обёртка исполнения, чтобы агент не изобретал JDBC-вызов
```

Обоснование:

- **Исполнение выносится отдельно и один раз.** Иначе описание подключения
  рассинхронизируется между скиллами. Агент вызывает `scripts/vql run file.vql`
  вместо сборки JDBC-подключения с нуля. Там же живёт разбор ошибок Denodo — именно
  на итерациях «выполнил → упало → чиню» сгорают токены, которых надо избежать.
- **Доменные скиллы получают точные триггеры**, но не дублируют общее — ссылаются
  на ядро.
- **Подтипы источников уходят в `references/`, а не в отдельные скиллы.**
  JDBC-источник и JSON-источник — один рабочий процесс с разными параметрами;
  разносить их по скиллам значит плодить почти одинаковые описания, между которыми
  агент будет промахиваться.

### Идея, которую стоит заложить

В каждом скилле держать **два уровня детализации**: минимальный рабочий шаблон и
полный набор опций с пометками о том, что реально генерирует Design Studio. Агент
читает минимальный, а в полный лезет только на нестандартных задачах.

## Срабатывание скиллов без явного указания (обсуждено)

Вопрос: если сказать просто «создай вью» в контексте Denodo — поймёт ли агент,
какой скилл вызвать?

Механика: до чтения скилла модель видит **только `description` из фронтматтера**,
содержимое `SKILL.md` в этот момент невидимо. Значит выбор скилла целиком
определяется качеством описаний, написанных под реальные формулировки задач, а не
под терминологию документации.

**Проблема со словом «вью».** В Denodo оно перегружено: base view (обёртка над
таблицей источника через wrapper), derived view (`CREATE VIEW ... AS SELECT`),
interface view (контракт без реализации), materialized/summary view (про
производительность). Пути создания принципиально разные: base view требует уже
существующих datasource и wrapper. Поэтому граница между `denodo-datasources` и
`denodo-views` проходит не там, где интуитивно кажется.

**Принятая трактовка:** «создай вью» по умолчанию означает **derived view** — base
views в реальной работе создаются пачкой при подключении источника, а не поштучно.
`denodo-views` ведёт в derived, а его `SKILL.md` начинается с короткой развилки
«если нужен base view — иди в `denodo-datasources`».

**Три приёма для надёжного срабатывания:**

1. **В `description` — глаголы задачи и VQL-команды, а не название сущности**, плюс
   явное отрицание. Пример:

   ```yaml
   # denodo-views
   description: Использовать при создании или изменении представлений в Denodo —
     derived views (selection, join, union, minus, intersection, flatten),
     interface views, CREATE VIEW ... AS SELECT. Также когда пользователь говорит
     "создай вью", "сделай витрину", "собери джойн" в контексте Denodo.
     Не для base views поверх источника — это denodo-datasources.
   ```

   Строка «не для X — используй Y» работает лучше, чем попытка идеально описать
   границу.

2. **Ядро `denodo-vql` как страховочная сеть** — нарочно широкий триггер («любая
   работа с Denodo или VQL»). При неоднозначной формулировке агент попадает в ядро,
   а ядро содержит карту скиллов. Цена промаха — одно лишнее чтение небольшого
   файла вместо VQL, сгенерированного по памяти.

3. **Непересекающиеся словари в описаниях.** Если слово встречается в двух
   `description` — одно из них переписывается.

**Проверка, а не угадывание.** У плагинов Claude Code есть механизм eval-сьютов
(`claude plugin eval`) и диагностика `/skill-doctor`. В репозитории с самого начала
держим набор реальных фраз — «создай вью», «подключи оракл», «заведи папку под
витрины», «сделай тег» — и проверяем, что срабатывает нужный скилл. Это же
становится регрессионным тестом при добавлении скиллов после v1, когда описания
начнут конкурировать друг с другом.

Гарантии нет ни у одного варианта, но у C она **измерима**, а промах стоит дёшево
благодаря ядру.

## Секция 1 дизайна: структура репозитория и упаковка (УТВЕРЖДЕНО)

**Поправка к варианту C:** плагинные скиллы автоматически получают namespace плагина.
Скилл в `skills/views/` внутри плагина `denodo` становится `/denodo:views`. Директория
`denodo-views` дала бы `/denodo:denodo-views`, поэтому префиксы из имён директорий
убраны.

```
denodo_skills/                        репо = плагин = маркетплейс
├── .claude-plugin/
│   ├── plugin.json                   name: denodo
│   └── marketplace.json              один плагин, source: "./"
├── skills/
│   ├── vql/SKILL.md                  /denodo:vql          ядро: конвенции, карта, цикл работы
│   ├── query/                        /denodo:query        диалект и выражения (v1 — минимум)
│   │   ├── SKILL.md
│   │   └── references/               datetime, string, nested, analytic, context, delegation
│   ├── execute/                      /denodo:execute      применение к живому VDP
│   │   ├── SKILL.md
│   │   └── references/errors.md      разбор ошибок Denodo
│   ├── catalog/SKILL.md              /denodo:catalog      базы, папки, теги
│   ├── datasources/                  /denodo:datasources  источники, wrappers, base views
│   │   ├── SKILL.md
│   │   └── references/               jdbc, json, xml, df, excel, odata, s3
│   └── views/                        /denodo:views        derived, interface
│       ├── SKILL.md
│       └── references/               derived, base, interface
├── scripts/
│   └── vql                           обёртка исполнения VQL
├── evals/                            eval-сьют: фраза → ожидаемый скилл
├── README.md
└── LICENSE
```

**Три следствия из спецификации Claude Code, зафиксированные в дизайне:**

1. **`${CLAUDE_PLUGIN_ROOT}` решает проблему вызова скрипта.** Путь до `scripts/vql`
   меняется при каждом обновлении плагина, но переменная подставляется и в теле скилла,
   и в `allowed-tools`. Скилл `execute` объявляет
   `allowed-tools: Bash(${CLAUDE_PLUGIN_ROOT}/scripts/vql *)` — и агент выполняет VQL
   без permission-prompt на каждый вызов. Снимает основное трение цикла
   «выполнил → упало → чиню».
2. **Содержимое скилла попадает в контекст один раз и не перечитывается** на
   последующих ходах. Скиллы пишутся как постоянно действующие правила, а не как
   одноразовый пошаговый рецепт.
3. **Бюджет `description` — 1536 символов** в листинге скиллов (обрезается совместно с
   `when_to_use`). Хватает и на триггерные фразы, и на строку «не для X — используй Y».

**Дистрибуция:** репозиторий одновременно плагин и маркетплейс, отдельный
репозиторий-каталог не нужен. Установка у пользователя —
`/plugin marketplace add kirivandubai/denodo_skills`, затем `/plugin install denodo@<маркетплейс>`.

## Скилл `query`: диалект и выражения (место зарезервировано, v1 — минимум)

**Решение: отдельный скилл, не в ядре и не внутри `views`.**

- *Не в ядре* — ядро читается почти всегда и должно оставаться маленьким. Справочник по
  диалекту (даты, строки, регулярки, вложенные структуры, аналитика, приведение типов,
  NULL-семантика) — самый объёмный материал набора; в ядре за него пришлось бы платить
  на каждой задаче, включая «заведи папку».
- *Не в `views`* — диалект нужен и вне создания объектов: посмотреть данные, отладить
  выражение, проверить гипотезу. Спрятав его в `views`, мы сделали бы знание
  недоступным там, где оно нужно чаще всего.
- Он **ортогонален классам объектов**: выражения используются в derived views, в
  row/column restrictions, в summary views, в условиях кэша.

**Граница `query` ↔ `views` проходит по `AS`:** `views` отвечает за DDL-обёртку
(`CREATE VIEW ... FOLDER ... AS`), `query` — за то, что внутри (SELECT, выражения,
функции). Скиллы ссылаются друг на друга одной строкой.

**Принцип содержания: не справочник, а дельта от стандартного SQL.** Пересказывать
полный список функций бессмысленно — модель значительную часть стандартного SQL знает.
Ценность в том, **где Denodo отличается от того, что модель угадает по привычке из
Postgres или Oracle**: там агент ошибается уверенно и молча, пишет правдоподобное имя
функции, которого в VQL нет, и узнаёт об этом только от сервера. Каждая такая ошибка —
лишняя итерация. Состав дельты: функции с другими именами (прежде всего даты и строки),
типы Denodo и правила приведения, работа с вложенными структурами, `CONTEXT (...)`,
делегирование в источник и диагностика pushdown.

Реверс из экспортов Design Studio особенно полезен именно здесь: студия генерирует
канонический VQL с конструкциями, которых по документации не угадать.

**Приоритет в v1 (решение пользователя):** `query` — не первоочередное, SELECT
достаточно просто написать и по документации. В v1 закладываем **минимальную дельту**,
объём пересматриваем позже. Фокус v1 — сценарий вайб-кодинга: **описал текстом →
объекты появились на платформе**.

## Секция 2 дизайна: ядро `/denodo:vql` (УТВЕРЖДЕНО)

Отличие от роутера-оглавления варианта A: оглавление — это последние шесть строк файла.
Тело — четыре вещи, которые не растут при добавлении новых доменных скиллов и
действуют постоянно.

**1. Рабочий цикл — это и есть вайб-кодинг на Denodo.**

Ключевое правило: **агент пишет VQL в файл проекта, а не выполняет из головы.**

```
намерение текстом
  → определить размещение (база, папка) по конвенциям
  → написать .vql в репозиторий проекта
  → применить через /denodo:execute
  → проверить, что создалось (DESC / пробный SELECT)
  → файл остаётся в git
```

Без этого правила вайб-кодинг даёт объекты, существующие только на стенде и ни в одном
артефакте: их нельзя отревьюить, перенести в другую среду или воспроизвести после
отката. С правилом сессия «наболтал витрину» оставляет версионируемый скрипт.

**2. Конвенции именования и раскладки.** Префиксы объектов, слои (подключение →
интеграция → бизнес), структура папок. Без них агент каждую сессию изобретает свою
схему, и каталог превращается в свалку — а Denodo-проекты живут годами.

*Решение по источнику конвенций:* **дефолт в ядре + переопределение проектом.** В ядре
лежит набор по умолчанию (на основе best practices Denodo); проект может положить свой
файл, агент читает его и перекрывает дефолты. Работает из коробки, но ничего не
навязывает командам со своими стандартами.

**3. Правила безопасности.** `CREATE` нового объекта — агент делает сам. `DROP`, `ALTER`
существующего, любое действие в среде с признаком прода — только после явного
подтверждения. Для публичного плагина обязательно: его поставят на боевые стенды.

**4. Идемпотентность.** Как писать VQL, переживающий повторное применение. Что именно
Denodo 9.5 поддерживает из `CREATE OR REPLACE` / `IF NOT EXISTS` — проверяем на стенде,
здесь возможны различия по типам объектов.

## Секция 3 дизайна: слой исполнения (УТВЕРЖДЕНО)

### Транспорт: официальный `denodo-sqlalchemy`

**Отвергнуто: JDBC.** Требует Java и `denodo-vdp-jdbcdriver.jar`, который нельзя
распространять в публичном open-source плагине по лицензии Denodo.

**Отвергнуто: вендоринг pure-Python драйвера.** Рассматривался путь «ноль установок»:
Denodo слушает PostgreSQL wire protocol на порту 9996, поэтому теоретически подходит
`pg8000` (BSD 3-Clause, 58 КБ, `py3-none-any` — без C-расширений) вместе с `scramp`,
`asn1crypto`, `python-dateutil`; суммарно ~440 КБ, все лицензии допускают вендоринг.
**Отклонено по решению пользователя:** Denodo реализует протокол PostgreSQL частично и
официально поддерживает psycopg2, а не произвольный клиент — риск не оправдан. Кроме
того, теряется расширяемость экосистемы SQLAlchemy (flightsql, pandas, пулы соединений).

**Принято: официальный `denodo-sqlalchemy`.** Даёт вторую точку расширения бесплатно —
тот же диалект умеет `denodo+psycopg2` (порт 9996) и `denodo+flightsql` (порт 9994,
VDP 9.1+). Переключение строкой в профиле среды, без правки кода.

### Установку делает скрипт, а не человек

Требование «без установок руками» выполняется не вендорингом, а самонастройкой
окружения:

```
scripts/denodo          тонкий launcher, только stdlib — не падает никогда
   │
   ├─ есть uv?          → uv run с inline-зависимостями (PEP 723)
   ├─ иначе             → venv в ${CLAUDE_PLUGIN_DATA}, пакеты ставятся один раз
   └─ не вышло          → одна строка с точной командой установки
```

`${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/denodo/`) — персистентная директория
плагина, **переживающая его обновления**: venv создаётся при первом запуске и дальше
переиспользуется. Пользователь ничего не ставит руками, при этом мы на официально
поддерживаемом клиенте.

Launcher обязан быть на голой стандартной библиотеке — иначе упадёт раньше, чем успеет
починить окружение.

### Расширяемость закладывается структурно

Часть функциональности (Data Marketplace, каталог) через VQL недоступна — поэтому
транспорты за общим интерфейсом, а не один жёстко зашитый канал:

```
denodo_cli/
  transports/
    vql_psycopg2.py     denodo+psycopg2, порт 9996        (по умолчанию)
    vql_flightsql.py    denodo+flightsql, порт 9994       (VDP 9.1+)
    api_rest.py         REST: Data Marketplace, каталог   (то, чего нет в VQL)
```

Единый контракт `execute(vql) -> rows | error`. Новый транспорт — это один файл и
строка в профиле среды, не правка скиллов.

```
scripts/denodo vql run   --env dev model/sales/views.vql
scripts/denodo vql desc  --env dev bv_orders
scripts/denodo api get   --env dev /marketplace/...
```

### Правила слоя исполнения

- **Креденшелы только через профиль среды и окружение, никогда в аргументах команды** —
  пароль в аргументе `Bash` оседает в транскрипте сессии. В команде фигурирует только
  имя профиля.
- **Профиль среды несёт флаг `production: true`** — иначе правило безопасности из ядра
  не имеет опоры: агент должен знать, куда подключён, до выполнения.
- Короткие команды чисто ложатся в предодобрение
  `allowed-tools: Bash(${CLAUDE_PLUGIN_ROOT}/scripts/denodo *)` — без permission-prompt
  на каждой итерации.
- Вывод машинночитаемый, чтобы агент не парсил простыню.
- Ошибки Denodo — в `references/errors.md`: код → что означает на самом деле → что
  чинить. Читается ровно в момент неудачной итерации, окупается быстрее прочих файлов.

### Риск №1 и первый шаг реализации

**Спайк №1:** подключить `denodo-sqlalchemy` к живому стенду и выполнить по очереди
`SELECT 1`, `CREATE VIEW`, `CREATE DATASOURCE`.

Единственный по-настоящему открытый вопрос: **пропускает ли канал 9996 полноценный
DDL**, или часть операций придётся уводить в `api_rest`. Ответ определяет, насколько
нагружен REST-транспорт в v1. Права пользователя на стенде тоже влияют на результат.

## Секция 4 дизайна: формат доменного скилла (УТВЕРЖДЕНО)

Единый скелет для `catalog`, `datasources`, `views` — пять блоков в фиксированном
порядке:

```
1. Развилка            «это про X; если тебе нужен Y — /denodo:Y»   (3–5 строк)
2. Минимальный шаблон  рабочий VQL сразу, без предисловий
3. Что нужно выяснить  чего не хватает для заполнения шаблона
4. Куда идти дальше    ссылки на references для нестандартных случаев
5. Проверка            как убедиться, что объект создан правильно
```

**Блок 3 отличает рабочую процедуру от справочника** и критичен для вайб-кодинга. На
фразе «подключи оракл» агенту не хватает хоста, порта, схемы и учётки. Скилл явно
разделяет: что берётся **из профиля среды**, что **из конвенций**, что **придётся
спросить у человека**. Иначе агент либо выдумает значения, либо устроит допрос из
десяти вопросов подряд.

**Порядок и зависимости — тоже в скилле.** Цепочку `datasource → wrapper → base view`
агент должен знать до начала, иначе упрётся в ошибку на втором шаге.

**Каждый шаблон несёт статус верификации:**

```sql
-- verified: 9.5 (стенд, 2026-09-XX)
CREATE DATASOURCE JDBC ...

-- unverified: только по документации 9.5
CREATE DATASOURCE JDBC ... WITH SOME_EXOTIC_OPTION ...
```

Непроверенный шаблон — не повод его не давать, но повод агенту быть осторожнее и
внимательнее проверить результат. Заодно даёт честный трекинг прогресса: видно,
сколько шаблонов реально прогнано на стенде.

**Два уровня детализации** (решение из раздела про вариант C): минимальный рабочий
шаблон в `SKILL.md`, полный набор опций с пометками о том, что генерирует Design
Studio, — в `references/`.

## Секция 5 дизайна: верификация и eval-сьют (УТВЕРЖДЕНО)

Две независимые проверки, ловят разные поломки.

**Верификация VQL: работают ли шаблоны.** Отдельная тестовая база на стенде
(`denodo_skills_test`), скрипт `scripts/denodo verify` прогоняет шаблоны и чистит за
собой. Результат прогона обновляет пометки `verified:` в файлах.

Неочевидный рычаг: **синтаксис источников проверяется без самих источников.**
`CREATE DATASOURCE JDBC` с заведомо недоступным хостом всё равно проходит парсер
Denodo — ошибка возникает на подключении, а не на разборе DDL. Значит корректность
синтаксиса для Oracle, S3, Salesforce подтверждается без наличия Oracle, S3 и
Salesforce. Реальные системы нужны только для проверки интроспекции и маппинга типов;
такие шаблоны помечаются как требующие живого источника.

**Eval-сьют: срабатывает ли нужный скилл.** Набор фраз → ожидаемый скилл, прогон через
`claude plugin eval`. Регрессионный тест на описания: когда после v1 добавятся
`security` или `performance`, их `description` начнут конкурировать с существующими, и
без сьюта деградация пройдёт незаметно.

## Секция 6 дизайна: что осознанно НЕ входит в v1 (УТВЕРЖДЕНО)

- **полный справочник функций** — `query` в v1 несёт только минимальную дельту;
- **производительность и кэш** — summary views, materialized tables, remote tables, MPP;
- **безопасность и публикация** — пользователи, роли, привилегии, row/column
  restrictions, REST/SOAP/GraphQL/OData сервисы;
- **Scheduler, Solution Manager, деплой между средами**;
- **flightsql-транспорт** — заложен структурно, но не реализуется;
- **свой MCP-сервер** — решение первого раздела; пересматривается только при появлении
  задачи, которую скилл плюс скрипт закрыть не могут;
- **версии Denodo кроме 9.5**.
