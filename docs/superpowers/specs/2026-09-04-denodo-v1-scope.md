# Объём v1: перечень объектов Denodo

**Дата:** 2026-09-04
**Статус:** решение принято
**Основание:** задача T1 трекера; уточняет раздел 12 [дизайн-документа](2026-09-04-denodo-skills-design.md)

---

## 1. Критерий отбора

Объект входит в v1, если без него нельзя довести до конца сценарий «описал текстом → на
платформе появилась работающая витрина». Всё, что улучшает уже работающий сценарий, —
не v1.

Исходно предполагалось 5–10 объектов. Итоговый перечень — шестнадцать: в объём решено
включить Data Marketplace, а это отдельный сервер платформы со своим набором сущностей.
Расширение осознанное, и его цена вынесена в раздел 3 — порядок сборки, при котором
работающее ядро появляется раньше полного перечня.

Целевая версия — Denodo 9.5. Все команды ниже сверены с документацией 9.5; пометка
`verified:` в шаблонах проставляется отдельно, по результату прогона на стенде
(раздел 11.1 дизайн-документа).

## 2. Перечень

Колонка «верификация» отвечает на вопрос из раздела 11.1: нужен ли живой внешний
источник, или достаточно того, что DDL проходит парсер Denodo.

### 2.1 `catalog` — Virtual DataPort, VQL

| Объект | Команда | Верификация |
|---|---|---|
| Виртуальная база | `CREATE [OR REPLACE] DATABASE` | полностью, без внешних систем |
| Папка | `CREATE [OR REPLACE] FOLDER` | полностью, без внешних систем |
| Тег VDP | `CREATE [OR REPLACE] TAG` / `CREATE TAGS`, `ALTER TAG`, `DROP TAG [IF EXISTS]` | полностью, без внешних систем |

Теги назначаются на представления и колонки через `ADD_TO (VIEWS (...) COLUMNS (...))
REMOVE_FROM (VIEWS (...) COLUMNS (...))` — на 9.5.1 **оба блока обязательны, каждый с
обеими секциями**, даже пустыми; представления и колонки только с именем базы
(спайк T2). Альтернатива — `TAGS (<tag>)` прямо в `CREATE VIEW`. Тег VDP и тег Data
Marketplace — **разные объекты в разных серверах**, см. 2.4.

### 2.2 `datasources` — Virtual DataPort, VQL

| Объект | Команда | Верификация |
|---|---|---|
| JDBC-источник | `CREATE [OR REPLACE] DATASOURCE JDBC` | синтаксис — без источника |
| JDBC-wrapper | `CREATE [OR REPLACE] WRAPPER JDBC` | синтаксис — без источника; рабочий `SELECT` — только с живой СУБД |
| Файловый источник | `CREATE [OR REPLACE] DATASOURCE DF` | полностью, локальный файл на стенде |
| Файловый wrapper | `CREATE [OR REPLACE] WRAPPER DF` | полностью |
| JSON-источник | `CREATE [OR REPLACE] DATASOURCE JSON` | полностью, локальный файл |
| JSON-wrapper | `CREATE [OR REPLACE] WRAPPER JSON` | полностью |
| Базовое представление | `CREATE [OR REPLACE] TABLE ... ADD SEARCHMETHOD ... WRAPPER (...)` | наследует от wrapper |

Два файловых типа взяты сознательно: DF даёт плоскую схему и самый частый файловый
сценарий, JSON — вложенную схему и HTTP-источник. Порядок создания — `datasource →
wrapper → base view` — фиксируется в самом навыке.

Файловые источники ценны ещё и тем, что замыкают сценарий целиком на пустом стенде: без
них любая приёмка требует внешней СУБД.

### 2.3 `views` — Virtual DataPort, VQL

| Объект | Команда | Верификация |
|---|---|---|
| Производное представление | `CREATE [OR REPLACE] VIEW ... FOLDER ... AS SELECT` | полностью, без внешних систем |
| Интерфейсное представление | `CREATE [OR REPLACE] INTERFACE VIEW` | полностью, без внешних систем |
| Ассоциация | `CREATE [OR REPLACE] ASSOCIATION ... REFERENTIAL CONSTRAINT` | полностью, без внешних систем |

Ассоциация отнесена к `views`, а не к `catalog`: она связывает представления и создаётся
после них — в цепочке зависимостей её место рядом с производным представлением.

### 2.4 `marketplace` — Data Marketplace, REST

| Объект | Канал | Верификация |
|---|---|---|
| Тег маркетплейса | `POST /public/api/tags`, назначение `POST /public/api/tags/{tagId}/views` | требует запущенного Data Marketplace |
| Категория | `POST /public/api/category-management/categories`, назначение `POST …/categories/{categoryId}/views` | требует запущенного Data Marketplace |
| External element (asset extension) | цепочка: `POST /public/api/external-elements-types` → `POST /public/api/external-providers-types` (multipart) → `POST /public/api/external-tool-servers` (`type: CUSTOM`) → VQL из `GET …/{id}/vql-metadata` и реализация interface view → `POST /public/api/external-tool-servers/synchronize` | требует Data Marketplace; external tool server создаётся самой цепочкой |

**Сигнатуры сняты с OpenAPI живого сервера и подтверждены на стенде** — спайк T11,
[отчёт](2026-09-08-spike-t11-marketplace-api.md). Базовый путь `/denodo-data-catalog`
сохранил историческое имя. Аутентификация — HTTP Basic учёткой VDP; `serverId`
необязателен при одном зарегистрированном сервере. External element в 9.5 не создаётся
напрямую: маркетплейс импортирует его из interface view VDP, поэтому «команда» у него —
цепочка, а не вызов.

**Теги маркетплейса — не теги VDP.** Data Marketplace ведёт собственный список тегов; те,
что импортированы из Virtual DataPort, помечены отдельной иконкой, и редактирование с
назначением у них отключены. Навык обязан разводить два случая: разметка объектов VDP —
это `catalog` и VQL, разметка витрины в маркетплейсе — это `marketplace` и REST.

Asset extensions в документации 9.5 названы **external elements**: ресурсы внешних
инструментов с 360-графом связей, категориями, тегами и пользовательскими свойствами.

## 3. Порядок сборки

Перечень из шестнадцати объектов собирается в два приёма. Смысл разделения — получить
работающий сквозной сценарий до того, как будет написан последний шаблон.

**Веха A — ядро работает.** Шесть объектов минимальной цепочки: виртуальная база, папка,
файловый источник, wrapper, базовое представление, производное представление. Веха
закрыта, когда одна фраза на естественном языке доводится до витрины с проверкой
`SELECT` (задача T13). **Закрыта 2026-09-12:** три приёмочных прогона на стенде 9.5.1,
по одной фразе каждый, довели цепочку до читающейся витрины; замер и найденные пробелы —
в записи T13 [трекера](../../TASKS.md).

**Веха B — полный перечень.** Остальные десять объектов, включая всю
marketplace-часть.

Marketplace отнесён к вехе B по двум причинам: он не участвует в приёмочном сценарии, и
он единственный, чьи сигнатуры вызовов неизвестны до спайка.

## 4. Рассмотрено и не вошло

Границы из раздела 12 дизайн-документа действуют без изменений: производительность и кэш
(summary views, materialized tables, remote tables, MPP), безопасность и привилегии
(пользователи, роли, row/column restrictions), публикация веб-сервисов, Scheduler и
Solution Manager, версии Denodo кроме 9.5.

Сверх этого при отборе рассмотрены и отклонены:

| Объект | Причина |
|---|---|
| Источники ODBC, XML, Excel, OData, S3, Salesforce, MongoDB, LDAP | Не требуют новой архитектуры: тот же формат навыка, те же три шага. Добавляются после v1 без правки ядра |
| Metric views | Надстройка над производным представлением; сценарий витрины замыкается без неё |
| Stored procedures, JMS/Kafka listeners, maps, JAR-расширения, пользовательские типы | Не участвуют в сценарии витрины. Решение в силе; процедуры при этом сделаны отдельным навыком вне v1 — T14, см. раздел 12 дизайн-документа |
| Statistics, индексы | Улучшают уже работающую витрину — по критерию отбора это не v1 |
| Scheduler API, Solution Manager API | Другие серверы платформы. Войдут тем же способом, что и Marketplace: новый транспорт плюс новый навык, без правки ядра и формата навыка |

Последняя строка — не отсрочка, а проверка архитектуры. Включение Marketplace показало,
что добавление сервера платформы обходится одним транспортом и одним навыком; если для
Scheduler это окажется не так, дело в формате навыка, а не в Scheduler.

## 5. Следствия для дизайн-документа

Внесено в [дизайн-документ](2026-09-04-denodo-skills-design.md) этой же задачей:

- **раздел 4** — в карту навыков добавлен `/denodo:marketplace`;
- **раздел 5** — в структуру репозитория добавлена `skills/marketplace/`;
- **раздел 6.4** — зафиксирован дефолт идемпотентности: `CREATE OR REPLACE` поддерживают
  все двенадцать VQL-объектов v1 (по документации 9.5; подтверждение на стенде — T2);
- **раздел 8** — «минимальный шаблон» больше не обязан быть VQL: это либо VQL, либо
  HTTP-вызов, статус `verified:` работает одинаково для обоих;
- **раздел 11.1** — верификация распространена на HTTP-шаблоны;
- **раздел 12** — Marketplace включён в границы v1;
- **раздел 13** — добавлен риск: сигнатуры Marketplace API не документированы публично.

Транспортный слой правки не потребовал: раздел 7.3 уже описывает `api_rest.py` и команду
`scripts/denodo api`.
